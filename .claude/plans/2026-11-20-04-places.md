## What globalping.io does (looked at 2026-11-20)

- Its Location box is a combobox: "Try one of these suggestions or use your own value." Free
  text still goes through.
- It loads Globalping's whole probe list (`/v1/probes`, 2.3 MB) into the browser once and
  matches it as you type. No search API.
- Suggestions come in groups (States, Cities, Countries, Networks), up to 8 each, each with
  where it is and its probe count: "Bangkok, Thailand (TH) 32", "Virginia (US-VA) 91",
  "Amazon.com 58".
- It matches the place around a name too: "bang" gives Dhaka (in Bangladesh); "virg" gives
  Ashburn (in Virginia).
- Picking fills in Globalping's location text: `Bangkok+TH`, `Ashburn+US-VA`, `Amazon.com`.
  `+` narrows ("California+Eyeball"); a comma gives several places ("USA, Canada, Mexico").
- What it doesn't offer: continents and regions by name, cloud regions (`aws-ap-southeast-1`),
  home or data centre networks, and anything of Cloudflare's.

## Same code everywhere

One search function, pure, with no Worker or browser in it (`src/places/search.ts`):

- The Worker runs it for `GET /api/places?q=…`, which the CLI and MCP call.
- The picker runs the same function in the browser, over the places from the same API
  (`GET /api/places`, no filter: all of them, about 3,300, cached), fetched once when the box is
  first used. Typing then answers at once, as globalping.io's does, with no call per key.
- One list of places, read once from Globalping's list (the same cached read the coverage map
  uses), plus Cloudflare's data centres (the same placed list the coverage map draws).
- The old ways go: free text you have to know, and each form's own idea of a place.

## What's wrong now

A place is typed as free text, and you have to know what Globalping accepts:

| Where                            | What you type                | What goes wrong                                                                              |
| -------------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------- |
| Probe page and `test --from`     | `TH`                         | Remembering codes; a typo or a place with no probes spends nothing but fails after the click |
| Runs page and `run --from`       | `TH`                         | The same                                                                                     |
| `run --everywhere --at`          | `BKK,SIN`                    | Remembering data centre codes                                                                |
| Map page and `remap --countries` | `TH,SG`                      | The same                                                                                     |
| Coverage                         | nothing: no way to narrow it | 220 KB for an agent that wanted one country                                                  |

## The idea: one thing, a place

A place is somewhere tests can run from, or a list can be narrowed to. Which places exist, and
their probes, come only from Globalping's probe list, so every place offered has probes in it.
Names come only from data, never from us (the user, 2026-11-20: "We shouldn't hard code anything
on our side"):

| Kind            | Example                       | Which exist, and probes | Name from                            | Count on 2026-11-20 |
| --------------- | ----------------------------- | ----------------------- | ------------------------------------ | ------------------- |
| Continent       | Asia (`AS`)                   | Globalping's probe list | countries-list `continents.min.json` | 6                   |
| Region          | South-eastern Asia            | Globalping's probe list | Globalping's own                     | 22                  |
| Country         | Thailand (`TH`)               | Globalping's probe list | countries-list `countries.min.json`  | 124                 |
| State (US only) | Virginia (`US-VA`)            | Globalping's probe list | OurAirports `regions.csv`            | 45                  |
| City            | Bangkok, Thailand (TH)        | Globalping's probe list | Globalping's own                     | 1,103               |
| Network         | Amazon.com (AS14618, AS16509) | Globalping's probe list | Globalping's own                     | 1,486               |
| Data centre     | BKK, Bangkok, Thailand        | Cloudflare's list       | Cloudflare's own                     | 345                 |

- countries-list is the list Globalping itself checks locations against (its `package.json`,
  2026-11-20). Every continent, country and US state code in Globalping's list is named: the
  real-data check (`vp run coverage:check`) proves it each time it runs.
- Held for later (the user: "I don't want us to make things too complicated"): cloud regions
  (`aws-ap-southeast-1`) and network types (home and mobile, or data centre). Both are in

## One search, everywhere

`searchPlaces` (`packages/shared/src/places.ts`): pure, the only matching code there is.

- **API:** `GET /api/places?q=bang&kind=city&limit=8` runs it in the Worker. Nothing asked:
  every place (about 3,100, 400 KB; Cloudflare compresses it). Open, spends no tests, cached
  (KV for the lists; the answer isn't, as Void never caches paths under `/api`).
- **CLI:** `cloudflare-ping places bang` (`--kind`, `--limit`, `--json`), through the API, shown
  in groups as the picker shows them (`groupByKind`), with what to pass as `--from`.
- **MCP:** the tool `places`, through the same command; at most 50 unless `limit` is given.
- **Pages:** the picker loads every place once from the same API and runs the same
  `searchPlaces` in the browser as you type: no call per key, as globalping.io does it.
- Ranking: an exact code first (`TH`, `BKK`, `AS13335`); names that start with what's typed; a
  word in the name; what it's within (`bang` finds Dhaka, in Bangladesh); anywhere in the name;
  more probes first among equals. Accents and capitals don't matter (`chisinau`).

## One filter, everywhere

The options are defined once, beside their command (`coverageOptions`,
src/commands/coverage-options.ts: `country`, and `cities`, left out unless asked, everywhere), and
read by the page's address, the API's query, the CLI's flag and the MCP tool's argument. Nothing
given: the whole list, as before.

- Coverage, by country: `/coverage?country=TH` (a link people can share; Void's ISR keeps each),
  `GET /api/coverage?country=TH`, `coverage --country TH`, the MCP tool's `country`. A country is
  the one kind both lists know: a data centre's country is its airport's; a probe city's is
  Globalping's. The page's map zooms to what's left, from the dots' own coordinates.
- A country by its code (`TH`) or its name as typed (`japan`, `thialand`), found by the one place
  search; none found: a 404 that says so.
- The options live on their own (src/commands/coverage-options.ts) so the page cache can read its
  keys: Void's ISR drops query parameters from its cache keys unless listed in
  `routing.revalidateQueryAllowlist` (guide/edge/revalidation.md), and without that every
  `/coverage?country=…` got the cached page for all countries (found on the live site,
  2026-11-20).
- Other kinds, and runs by where they ran from, when a list is long enough to need them.

## The picker: one component, every form

`src/PlacePicker.tsx`, one React component, used by every form. Built the Void way: the pages are
React pages Void hydrates, so the picker is an ordinary component in them; it reads places with
Void's typed `fetch` (`void/client`, `GET /api/places`) and hands its value to the page's
`useForm` (`form.setData`), so the form's action, errors and saved input work as now.

What it does, as globalping.io's Location box does (looked at 2026-11-20):

- **A text box first.** Typing `TH` and submitting works, with or without JavaScript, and
  before the places have loaded. "Try one of these suggestions or use your own value."
- **Places load once**, the first time the box is focused, then every keypress searches them in
  the browser with `searchPlaces`.
- **Suggestions in groups** (`groupByKind`, headings from `KIND_LABELS`), up to 8 of each, the
  group with the best match first. Each line: the name in bold, what it's within, and its probe
  count on the right: "**Bangkok**, Thailand (TH) 32".
- **Picking fills in Globalping's location text** (`Bangkok+TH`, `US-VA`, `Amazon.com`), shown
  as it will be sent, so what's sent is never a mystery.
- **Keyboard first:** down and up move through the suggestions, Enter picks, Escape closes, Tab
  leaves. An ARIA combobox (`role="combobox"`, a `listbox` of `option`s,
  `aria-activedescendant`), so screen readers say what's offered.
- **Which kinds each form offers:** a test's From offers what Globalping can run from
  (`FROM_KINDS`: everything but data centres); everywhere's "at" offers data centres; the Map
  page's countries offer countries.
- **Several places** where the form takes several (the Map page's countries, everywhere's data
  centres): each pick becomes a removable chip.
- **Looks:** the site's own styles (pages/style.css), light and dark, and at phone width the list
  fits the screen with no sideways scroll.

## Did you mean

Globalping accepts more than our places (tags, combinations), so nothing is refused before it's
sent. When Globalping has no probes for what was asked (`422`, `no_probes_found`: checked
2026-11-20, no test is spent), its refusal comes back with the places the one search finds for it:
"Did you mean Thailand (--from TH)?". The search finds a typo or two too ("thialand", "bankok"),
so the picker does as well. The page, CLI and MCP get the same words.
