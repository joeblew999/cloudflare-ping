# 2026-11-20-02-void-way.md: the app, the proper Void way

Status: 2026-11-20, approved (the user: "i want us to use proper void approach"). Steps 1 to 6
built, tried under `vp dev` and deployed the same day (below). One proof left: a real background
run on the deployed site, its fetches appearing on its page live (step 4). Each finding
below comes from checking the app against Void 1.10.0's docs (`node_modules/void/docs`) and its
`void` skill, which `void init` should have linked but never had. Its agent step ran in
`apps/web`, where there's no `.claude/`. It's now linked at the root, by Void's own code
(`linkSkillsForSpecificAgents`), as `.claude/skills/void`.

## Decided (the user, 2026-11-20)

- **Pages use Void's page actions and `useForm`** (`guide/pages-routing/actions-and-forms.md`;
  the skill: "In Pages, prefer the adapter's `Form` with `useForm()`").
  - Each page's `.server.ts` gets an `action` that runs the same shared action as its API
    route. So the web and the CLI still do the same thing from one implementation.
  - The CLI and MCP keep calling the API.
  - This replaces "the pages call the API" (main plan, How we use it).
- **A run's page follows its fetches with `void/live`** (`guide/live.md`), not by asking every 2
  seconds.
  - `/run` publishes each recorded fetch to the run's topic.
  - Void runs this on a Durable Object it manages. That replaces "no Durable Objects are used"
    for the app; the probe's own work still keeps nothing.
  - The CLI's `run` keeps following through the API. Void's live client needs `EventSource`,
    which Node 26 doesn't have.

## Found, and what changes

| Where        | Not the Void way                                                                   | The Void way                                                                                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Actions      | Each route's body holds the work.                                                  | `src/commands/` (not "actions": Void's word for a page's mutation): each written once, for its route, its page action and its MCP tool (plan 2026-11-20-01).                               |
| Forms        | `onSubmit` calls `/api/…` with `fetch`, then `window.location.assign`.             | `Form` + `useForm` to the page's `action`; the action redirects to the new run.                                                                                                            |
| Nav          | The active link is found by comparing the path, shared by `middleware/01.auth.ts`. | `Link` marks it (`aria-current`, `data-void-active`, `activeMatch="prefix"`); CSS styles those. `path` leaves the shared data.                                                             |
| Links        | `<a href={`/runs/${id}`}>`                                                         | `Link` with `routeUrl('/runs/[id]', { params })` (`guide/type-safety.md`).                                                                                                                 |
| Slow data    | The Runs page's Globalping limit is fetched in a `useEffect`.                      | `defer()` in the loader, read with `use()` under `Suspense` (`guide/pages-routing/loaders.md`).                                                                                            |
| Logs         | `console.log({ message, … })`                                                      | `logger` from `void/log`, one JSON line per call, `logger.child({ run })` (`reference/api/resources.md#logging`).                                                                          |
| Reading logs | Only `cf o11y telemetry query`.                                                    | `void project logs` for a live tail (`reference/cli/project.md`). Cloudflare targets have no history there, so Workers Logs stays for history.                                             |
| Head         | Viewport and favicon set in middleware.                                            | Site defaults in `void.config.ts` `head` (`lang`, viewport, icon, `titleTemplate`). Only the theme script stays in middleware, as Void's own example does (`guide/pages-routing/head.md`). |
| Errors       | Void's default pages.                                                              | `pages/_not-found.tsx` and `pages/_error.tsx`, in the app's frame and look (`guide/pages-routing/errors.md`).                                                                              |
| Starter      | `routes/api/hello.ts`, from `void init`.                                           | Removed.                                                                                                                                                                                   |
| Tests        | None.                                                                              | `vp test`, with `vite-plus/test`, in `tests/` or beside the code in `src/` (`guide/testing.md`).                                                                                           |
| New files    | Written by hand.                                                                   | Start from `void gen` where Void has a generator (`reference/cli/generate.md`).                                                                                                            |

## Build order

1. Actions written once; the routes become thin. Proof: the CLI's `--json` answers are
   unchanged.
2. Page actions and `useForm` on `/` and `/runs`. Proof: a probe and a run started from the
   pages, signed in, and refused when signed out.
3. Links, the nav, the deferred limit, the head, the error pages, and the logger; `hello.ts` goes.
4. `void/live` on a run's page. Proof: a background run's fetches appear without asking.
   - The deploy adds Void's Durable Object class. Void's docs say a class addition on an
     existing Worker is reviewed, then deployed with `--atomic`.
5. Tests (`vp test`) for the shared pieces and the actions; the `logs` task (`void project logs`).
6. README, docs and the main plan updated.

## Tried under `vp dev`, 2026-11-20

- The API answers as before:
  - the CLI's `runs`, `show` and `limits` read the same;
  - signed out, `POST /api/probe` and `GET /api/trace/<ray>` answer 401;
  - a missing run answers 404, as a page Void's `_not-found` in the app's frame.
- Every page has its own title (`… | cloudflare-ping`) and `<html lang="en">`.
- The bar: Runs carries `data-void-active` and `aria-current="page"` on `/runs`, and Probe
  doesn't.
- Home page, signed in: Run made the test (one Globalping test). The action redirected to
  `/?measurement=2q8gf7ARgeilkkwfH00021XJt#probe`, and the deferred answer arrived: Bangkok,
  AIS Fibre, "Same: answered BKK".
- Runs page:
  - the deferred limit read "249 of 250 tests left … in BKK";
  - a target not on the allowed list showed the refusal in the form, without spending a test;
  - a real start redirected to the new run's page.
- A run's page followed it live: fetches recorded by `/run` for that run appeared without a
  reload.
  - Two faults were found and fixed. A row without a `cf-ray` (only `vp dev`'s) crashed
    `routeUrl`. Re-subscribing on every router change looped, because `useRouter()` is a new
    object after each refresh; it now uses `useEffectEvent`.
  - After the fix: one subscribe, one refresh, and the fourth fetch arrived live.
- `vp test`: 3 files, 7 tests pass.
- The deploy adds Void's `VoidLiveStreamDurableObject` (SQLite, bound as `VOID_LIVE`), the one
  change to the Worker's config. A class addition, so it goes out with `--atomic`, as Void's docs
  say.
