## Decided (the user, 2026-11-20)

- **Pages use Void's page actions and `useForm`** (`guide/pages-routing/actions-and-forms.md`;
  the skill: "In Pages, prefer the adapter's `Form` with `useForm()`").
  - Each page's `.server.ts` gets an `action` that runs the same shared action as its API
    route. So the web and the CLI still do the same thing from one implementation.
  - The CLI and MCP keep calling the API.
  - This replaces "the pages call the API" (main plan, How we use it).
- **A run's page follows its fetches with `void/live`** (`guide/live.md`), not by asking every 2
  seconds.
  - `/run` publishes each recorded fetch to the run's topic.
  - Void runs this on a Durable Object it manages. That replaces "no Durable Objects are used"
    for the app; the probe's own work still keeps nothing.
  - The CLI's `run` keeps following through the API. Void's live client needs `EventSource`,
    which Node 26 doesn't have.

## Found, and what changes

| Where        | Not the Void way                                                                   | The Void way                                                                                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Actions      | Each route's body holds the work.                                                  | `src/commands/` (not "actions": Void's word for a page's mutation): each written once, for its route, its page action and its MCP tool (plan 2026-11-20-01).                               |
| Forms        | `onSubmit` calls `/api/…` with `fetch`, then `window.location.assign`.             | `Form` + `useForm` to the page's `action`; the action redirects to the new run.                                                                                                            |
| Nav          | The active link is found by comparing the path, shared by `middleware/01.auth.ts`. | `Link` marks it (`aria-current`, `data-void-active`, `activeMatch="prefix"`); CSS styles those. `path` leaves the shared data.                                                             |
| Links        | `<a href={`/runs/${id}`}>`                                                         | `Link` with `routeUrl('/runs/[id]', { params })` (`guide/type-safety.md`).                                                                                                                 |
| Slow data    | The Runs page's Globalping limit is fetched in a `useEffect`.                      | `defer()` in the loader, read with `use()` under `Suspense` (`guide/pages-routing/loaders.md`).                                                                                            |
| Logs         | `console.log({ message, … })`                                                      | `logger` from `void/log`, one JSON line per call, `logger.child({ run })` (`reference/api/resources.md#logging`).                                                                          |
| Reading logs | Only `cf o11y telemetry query`.                                                    | `void project logs` for a live tail (`reference/cli/project.md`). Cloudflare targets have no history there, so Workers Logs stays for history.                                             |
| Head         | Viewport and favicon set in middleware.                                            | Site defaults in `void.config.ts` `head` (`lang`, viewport, icon, `titleTemplate`). Only the theme script stays in middleware, as Void's own example does (`guide/pages-routing/head.md`). |
| Errors       | Void's default pages.                                                              | `pages/_not-found.tsx` and `pages/_error.tsx`, in the app's frame and look (`guide/pages-routing/errors.md`).                                                                              |
| Starter      | `routes/api/hello.ts`, from `void init`.                                           | Removed.                                                                                                                                                                                   |
| Tests        | None.                                                                              | `vp test`, with `vite-plus/test`, in `tests/` or beside the code in `src/` (`guide/testing.md`).                                                                                           |
| New files    | Written by hand.                                                                   | Start from `void gen` where Void has a generator (`reference/cli/generate.md`).                                                                                                            |

Already the Void way, checked:

- the folders (`reference/structure.md`);
- `env.ts` and `void/env`;
- secrets by `void secret put`;
- the database (`guide/database.md`, checked in full when the user asked):
  - the schema in `db/schema.ts` with `void/schema-d1`, imported through `@schema`;
  - `db` and the query operators from `void/db`;
  - every migration by `void db generate`; the one that drops a column carries Void's
    `-- void:allow-destructive`;
  - the seed (`defineSeed`);
  - the deployed database read with `void db execute --remote`.

  Two of its features aren't used, on purpose:
  - Schema-derived validators (`createInsertSchema`) fit an input that _is_ a table row. A run's
    input says `from` (the column is `fromPlace`), and the input's required fields are nullable
    columns. A probe has no table. Deriving them would mean overriding most fields.
  - Relational queries are optional in the guide; a run and its fetches are two small queries.

- auth through `defineAuth`;
- typed `fetch` from `void/client` in the CLI;
- `cloudflare.observability` passed through `void.config.ts`.

## The app at the root, 2026-11-20

The Void app moved from `apps/web` to the repo's root and the docs from `apps/docs` to `docs/`, as
Void's guide sets a static site beside an app (`guide/app-types.md`, "Adding a backend to a static
site"). Pushed first, and tagged `before-root-move`. The paths above, and in the other plans, are as
they were when written.

- Every Void and `vp` command runs at the root, as it is: no `vp -C apps/web`, no `web#`.
  `defaultPackage` (the root `vite.config.ts`) is `"."` for `vp dev`, `vp build` and `vp preview`.
- One thing Void's guide says doesn't work: VitePress in the app's own package, with
  `inference.appType: "void"`. Void 1.11.0's own check, run read-only on the root
  (`detectPreset(root, { strictBackend: true })`, which `void deploy --platform cloudflare` calls),
  refused: "vitepress was detected, but this project also has backend code". Its Cloudflare deploy
  never reads `appType`; only its platform deploy does. So `docs/` keeps its own `package.json`
  (VitePress, Vue), and the root's lists `docs` instead. With that, the same check refuses nothing.
- `void init --tsconfig` at the root wanted to copy `.void/tsconfig.json`'s paths and files into
  the root `tsconfig.json`, which already extends it, as Void's type-safety guide shows; left as
  the guide has it. The skill links (`.claude/skills`, not in git) now point at the root's
  `node_modules/void/skills`.
- Checked: `vp check` (155 files), `vp test` (44), `pnpm ready`, `vp build`, `vp pack`, `vp dev`
  (every page, the docs and the APIs: 200), `vp preview`, `docs:dev`, `docs:preview`, and the CLI
  from source against the live site.
- `vp run deploy` from the root went through first time: migrations up to date, staged, ready,
  live. Live: every page and docs page 200, missing ones 404, `/mcp` 401 with its sign-in link; the
  docs show the new paths. The CLI's `--json` and the API give identical answers, counts and all,
  for coverage (all, TH, Europe, Thailand, an unmatched place, with and without cities) and places
  (bang, th, europe, virginia).
- `/mcp` still needs the user's own sign-in: Claude Code lists the server as "Needs
  authentication" (`/mcp`, then Authenticate). It takes only OAuth tokens made for it, not the
  CLI's, so it can't be tested without that.
