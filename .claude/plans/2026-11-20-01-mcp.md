# 2026-11-20-01-mcp.md: the app as an MCP server, on its own Worker

Status: 2026-11-20, worked out, not built. The same day: how Void sets up agents, and the same
for our package, so any agent can use the app ("For any agent"). Found from Void 1.10.0's docs (`node_modules/void/docs`),
the packages' own READMEs and types, and Cloudflare's docs; nothing copied from other repos.

## What Void gives, and what it doesn't

Void has no MCP of its own: nothing in its docs, its `dist` or its skills. It doesn't need any.
Void already has the two pieces an MCP server is made of:

- **A route that answers a raw `Request`.** `routes/mcp.ts` exports `POST`, which hands
  `c.req.raw` to an MCP handler and returns its `Response` (Void: `guide/server-routing.md`).
- **Auth that is Better Auth.** `auth.ts` is `defineAuth`, which takes Better Auth's plugins as
  it already takes `bearer()` and `deviceAuthorization()`. `getAuth(c)` gives the request's
  Better Auth instance (Void: `guide/auth.md`). Void writes the plugins' tables into the
  migrations itself.

So the Void way is to use those two, with the libraries made to sit inside them:

- **Transport:** `@modelcontextprotocol/server` 2.4.0, the official SDK's version 2.
  `createMcpHandler(factory)` gives `handler.fetch(request, { authInfo })`. Its docs name
  Cloudflare Workers and Hono's `c.req.raw` as where that goes. It is stateless: a fresh server
  per request, which suits a Worker that keeps nothing (the main plan's idea). There are no
  sessions, no Durable Object, and no KV.
- **Auth:** `@better-auth/mcp` 1.7.25 (`mcp()`), built on `@better-auth/oauth-provider`. It
  turns Void's auth into the OAuth 2.1 server MCP clients sign in through, and binds each token
  to `/mcp`. `requireMcpAuth(auth, handler)` guards the route: a request without a token gets a
  401 that points the client at the sign-in. `@better-auth/cimd` 1.7.25 (`cimd()`) lets a
  client name itself by a URL (Client ID Metadata Documents), as MCP 2026-07-28 asks.
  `@better-auth/mcp`'s README names this exact pairing: "Serve MCP 2026-07-28 requests with
  version 2 of the official `@modelcontextprotocol/server` package … mount it behind
  `requireMcpAuth`, and expose only the HTTP `POST` route."

Not used, and why:

- **Cloudflare's `agents` (`McpAgent`, `createMcpHandler`).** It brings Durable Objects and
  about twenty optional peers. Its stateless handler does what the SDK's own does.
- **`@cloudflare/workers-oauth-provider`.** It wraps the Worker's whole entry, which Void owns.
  We'd also have a second sign-in beside Void's.

All the releases are more than a day old: the SDK 2.4.0 is from 2026-10-23; the Better Auth
plugins 1.7.25 are from 2026-11-14 and match the Better Auth 1.7.25 that Void 1.10.0 uses;
`@cfworker/json-schema` 4.1.6 is from 2026-11-04.

## How it fits the reuse we have

Today, each thing the app does is one API route, one page and one command (the main plan, "How
we use it"). The page and the command call the route; the route and the page loaders share
`src/`. MCP is a third caller of the same things, so each becomes one API route, one page, one
command and one tool.

The tools run inside the Worker, so they don't call the API over HTTP. That would be the
Worker fetching itself, signed in a second way. They do what the page loaders already do: they
call the same server code as the routes. To make "the same" true, not a copy, each action is
written once:

- **`apps/web/src/commands/<name>.ts`**, one per action (`test`, `run`, `runs`, `show`,
  `limits`, `trace`). Each holds:
  - its input as one zod schema;
  - whether it needs someone signed in;
  - what it does: the body of today's route, moved out, including the allowed-host checks,
    the `waitUntil` for a run's start, and the Globalping token.
- **The API route** becomes `withValidator({ body: action.input })`, then `requireAuth` where
  the action needs it, then the action. Its answer doesn't change, so the CLI's and the pages'
  typed `fetch` doesn't either.
- **The MCP tool**, in `apps/web/src/mcp.ts`: `registerTool(name, { inputSchema: action.input,
  description, annotations }, action)`, for each action.
  - The SDK takes zod schemas (Standard Schema), as Void's `withValidator` does, so one schema
    serves both.
  - The name and description come from `packages/shared/src/commands.ts`, the list that
    `cloudflare-ping help` and the docs' command reference already read. So the help, the docs
    and the tools can't differ.
  - The answer is the route's JSON, as `structuredContent`, with the same JSON as text.
- **The commands list** gains a `tool` column. Each command names its tool, as it names its
  page and route. `sign-in`, `sign-out` and `whoami` have none: an MCP client signs itself in.
- **Logs:** a tool call runs the same action, so it writes the same log lines under the run's
  ID. One line per call says it came through `/mcp`.

The words for a failure are the same too. A tool that fails answers `isError` with the
message the page and the CLI show (`packages/shared/src/failure.ts`).

## Signing in

There is one sign-in: Void's. `ALLOWED_EMAILS` still decides who can have an account, so an
MCP client can only act as an allowed account.

- `auth.ts` gains:
  - `jwt()`, which signs the access tokens;
  - `mcp({ loginPage: "/login", consentPage: "/consent", resource: "https://<site>/mcp" })`;
  - `cimd({ fetchClientMetadataResource, metadataProfile: "mcp-2026-07-28" })`.
- CIMD's own `fetchClientMetadataResource` is for Node: it uses `node:net` to pin a public
  address. On a Worker, `fetch` already can't reach private addresses, so ours is `fetch(url,
  { redirect: "manual" })` (it refuses redirects, as CIMD asks). This needs checking against
  Cloudflare's docs before it's trusted.
- Dynamic Client Registration is on too (`allowDynamicClientRegistration`,
  `allowUnauthenticatedClientRegistration`), so any agent can connect with only the URL ("For
  any agent," below).
  - Claude Code 2.1.312 knows CIMD (`client_id_metadata_document_supported` is in its binary),
    but many clients still register themselves the older way, by Dynamic Client Registration.
  - The cost: anyone can register a client. No one outside `ALLOWED_EMAILS` can sign one in, so
    a client registered by a stranger gets no token.
  - Native clients' `http://127.0.0.1` callbacks need `clientRegistrationDefaultApplicationType:
    "infer"`. The provider's docs name Cursor and older Claude Code.
- **`/login`** keeps its form but signs in through Void's auth client with the OAuth provider's
  client plugin (`createAuthClient` from `void/client`, plus `oauthProviderClient()`). In an
  OAuth flow, that plugin adds the flow to the sign-in, so signing in carries on to the client.
  Outside one, nothing changes.
- **`/consent`** is a new page: which client is asking, for whom, Allow or Deny
  (`/api/auth/oauth2/consent`). It looks like the other pages.
- **Discovery:** `.well-known` routes, which Void's routing keeps (`guide/server-routing.md`):
  - the authorization server's metadata (`oauthProviderAuthServerMetadata`);
  - the protected resource's metadata for `/mcp`.

  Their exact paths depend on the issuer, since Better Auth sits at `/api/auth`, so they're
  found when built.

- **The CLI and the pages are unchanged.** They keep their session tokens (`bearer()`,
  `deviceAuthorization()`); MCP tokens are JWTs for `/mcp` only. That the bearer plugin ignores
  a JWT it can't read is a check for the build.

## The route

```ts
// apps/web/routes/mcp.ts
export const POST = defineHandler((c) =>
  requireMcpAuth(getAuth(c), (request, claims) =>
    mcpHandler.fetch(request, { authInfo: toAuthInfo(claims) }),
  )(c.req.raw),
);
```

- Only `POST`; the SDK answers others 405.
- `legacy` is left at `"stateless"`, so clients still on MCP's 2025 revisions are served too,
  with the same tools, from the same factory. Switch to `"reject"` once the clients we use speak
  2026-07-28.
- JSON Schema checks use the SDK's Workers validator
  (`@modelcontextprotocol/server/validators/cf-worker`, with `@cfworker/json-schema`): its
  default, Ajv, compiles code at runtime, which Workers forbid.
- The Origin check the SDK asks for in front of a bare handler: an MCP client isn't a browser,
  so a request with an `Origin` that isn't ours is refused.
- A long tool (an inline run, up to about 90 seconds) answers when done. Progress notifications,
  which the SDK streams over SSE, are for later.

## Parity

- **README table:** an "MCP tool" column beside the page, the task, the command and the route.
- **Docs:**
  - the command reference shows each tool, from the same list;
  - a short page, "From an AI agent," gives the one line to add it:
    `claude mcp add --transport http cloudflare-ping https://cloudflare-ping.gedw99.workers.dev/mcp`.
    The client then opens `/login` in the browser.
- **`/mcp` in a browser** (a GET) is answered 405 by the SDK. The docs page is what a person
  reads.

## For any agent: how Void does it, and the same for us

### What Void does

Void ships everything for agents in its npm package. Its `files` are `docs/`, `skills/` and
`AGENTS_TEMPLATE.md`, beside the code (`node_modules/void/package.json`). `void init` then does
two things (`dist/init-*.mjs`, `dist/agents-*.mjs`, `dist/skills-*.mjs`;
`docs/integrations/agents.md`):

- **It writes a Void section into `AGENTS.md`**, keeping what else is there. The section points
  at `node_modules/void/docs/`. Most agents read `AGENTS.md`.
- **It links Void's skills (`void`, `migrate-vite-cloudflare-to-void`) for each agent it finds.**
  - It finds 19 agents by their folders in the app's root.
  - Claude Code's is `.claude/skills` (found by `.claude/` or `CLAUDE.md`).
  - Amp, Codex, Cursor, Gemini CLI, GitHub Copilot and opencode share `.agents/skills`.
  - Windsurf, Cline, Roo, Kilo Code, Continue, Goose, Trae, Junie, Kiro, Zencoder and Qwen Code
    each have their own (`.windsurf/skills` and so on).
  - The links are relative symlinks into `node_modules/void/skills/`. So a skill is always the
    installed Void's, and its paths to `docs/` hold.
  - A skill is a `SKILL.md`: a name, a one-line description, and which docs to read for what.
    It carries no second copy of the docs.

What Void doesn't ship:

- a Claude Code plugin or marketplace;
- MCP config;
- any MCP server.

A Void app's agents learn Void from skills and docs, which every agent above reads in the same
form.

In this repo, Void's agent step ran in `apps/web` (its `AGENTS.md`), where there's no
`.claude/`. So the `void` skill was never linked, and the agents working on this repo don't
have it. Linking it at the root (`.claude/skills/void` and `.agents/skills/void` →
`apps/web/node_modules/void/skills/void`), as `void init` would, is step 0 below.

### The same for cloudflare-ping

Two parts. Any agent gets both the same way.

**1. The MCP server: the tools, for any agent that speaks remote MCP.**

The only thing an agent needs is the URL, `https://cloudflare-ping.gedw99.workers.dev/mcp`.
Everything after it is standard, so no agent needs anything made for it:

- Streamable HTTP, served for the 2026-07-28 revision and, through the stateless fallback, the
  2025 ones.
- Sign-in found by OAuth discovery: the 401's `WWW-Authenticate`, then the two metadata
  documents.
- Registration by CIMD or by Dynamic Client Registration, whichever the agent does.

Claude Code: `claude mcp add --transport http cloudflare-ping <url>` (it does OAuth itself).
Others put the same URL in their own MCP settings. Their formats differ (Cursor's
`.cursor/mcp.json`, VS Code's `.vscode/mcp.json`, Gemini CLI's `settings.json`, Codex's
`config.toml`). Each one is checked against that agent's docs when it's added, not written from
memory.

**2. A skill: how to use the tools well, shipped in our package as Void ships its own.**

`packages/cli/skills/cloudflare-ping/SKILL.md`, in the `cloudflare-ping` package's `files`. It
says:

- what the app does;
- that a run or a test spends Globalping tests, so check `limits` first;
- background or inline;
- how to read a run (`show`, its page, its log lines by run ID);
- to use the MCP tools when connected, and the CLI's commands (`--json`) when not;
- where the docs are.

Its list of tools and commands is written from `packages/shared/src/commands.ts` when the
package is built (`vp pack`). So the skill, `help`, the docs and the tools come from one list.

**`cloudflare-ping init`: Void's agent step, for our package.** Run in a project that will use
the app, it does what `void init` does:

- finds the same agents by the same folders;
- links our skill into each one's skills folder (relative symlinks into
  `node_modules/cloudflare-ping/skills/`);
- adds a short section to `AGENTS.md`.

It also adds the MCP server for Claude Code (`.mcp.json`, the project scope `claude mcp add -s
project` writes). For each other agent found, it prints that agent's line. Each agent's file is
written only once its format is checked.

Void's table of agents is internal to Void (`dist/agents-*.mjs`, not exported), so ours is a
copy of its 19 entries, with where it came from. It's checked when Void is upgraded.

**A Claude Code plugin is a wrapper, later and optional.** Claude Code installs bundles (skills
plus MCP servers) from a marketplace (`claude plugin marketplace add <github repo>`, then
`claude plugin install`). The same `packages/cli` folder could be that plugin: add
`.claude-plugin/plugin.json` and a `.mcp.json` naming the URL, and the repo root gets
`.claude-plugin/marketplace.json`. It's the same skill and the same URL, so nothing is
duplicated. It's only for Claude Code, and the repo is private, so only people with access can
add it. It isn't needed for any agent to use the app; `claude plugin validate` checks it if it's
made.

## Build order, each proved before the next

New files start from Void's generators where it has one (`docs/reference/cli/generate.md`), then
get filled in:

- `void gen route mcp --methods post`, and `void gen route` for each `.well-known` document;
- `void gen middleware` if the Origin check becomes middleware.

The generated route is a stub of the same shape ours have (`defineHandler` from `void`, one
export per method), so the hand-written ones need no change. Other parts come from elsewhere:

- The auth tables' migration comes from `void db generate`, as every migration so far has.
- `void gen model` isn't used. Its tables add `updatedAt`, and its list, create and fetch routes
  aren't ours. The new tables are Better Auth's, which Void writes itself.
- Pages (`/consent`) have no generator; they're written as the other pages are.

0. **Void's own skill, for the agents working on this repo.** Link `void` at the root for
   Claude Code and `.agents/skills`, as `void init` would. Proof: the skill loads in a new
   session.

1. **Done 2026-11-20 (plan 2026-11-20-02): commands written once.** Move each route's body into
   `src/commands/`, so named because Void calls a page's mutation its "action". Routes become thin;
   nothing else changes. Proof:
   - `vp check`;
   - `cloudflare-ping runs/show/limits --json` give the same answers before and after;
   - a background run still records its fetches.
2. **`/mcp` with tools, behind a temporary check.** The tools come from the actions and the
   commands list. Until the OAuth step, `/mcp` takes the CLI's session token (`getUser()`), and
   locally only. Proof, against `vp dev`, with the SDK's client:
   - `tools/list` names the six tools, worded as `cloudflare-ping help`;
   - `limits` and `runs` answer as the CLI's `--json` does.
3. **Signing in by OAuth.** Add `jwt()`, `mcp()` and `cimd()`, the `/consent` page, `/login`'s
   client plugin, the `.well-known` routes and the migration. Proof, deployed:
   - without a token, `POST /mcp` answers 401 with a `WWW-Authenticate` that names the
     resource metadata, and both metadata documents answer;
   - `claude mcp add` (the line above), then signing in from the browser as the allowed
     account, connects;
   - an address not allowed gets no token.
4. **Used from Claude Code.** From Claude Code: list the tools, call `limits`, and start a
   background run with `run`. The run shows on `/runs` and in `cloudflare-ping show`, with its
   log lines. Proof: the run's ID in all three.
5. **Another agent, the same way.** One agent that isn't Claude Code (Cursor, VS Code or Codex,
   whichever is to hand) connects with only the URL and signs in. Proof: it lists the same six
   tools and calls `limits`.
6. **The skill and `cloudflare-ping init`.**
   - Build: the skill, written from the commands list at `vp pack`; `init`, which links it,
     writes `AGENTS.md`'s section and adds Claude Code's `.mcp.json`.
   - Proof, in an empty folder with `.claude/` and `.cursor/`:
     - `cloudflare-ping init` links the skill into `.claude/skills` and `.agents/skills`, and
       writes `.mcp.json`;
     - a new Claude Code session there loads the skill and the server.

## Open, for the build

- Whether Void sets Better Auth's `baseURL`, or works it out per request. `requireMcpAuth`
  takes the issuer and resource from it. If it's worked out per request, use
  `createMcpProtectedRequestHandler` with both given.
- Which way Claude Code registers: by CIMD (it knows it) or by Dynamic Client Registration. Both
  are on, so the build only needs to see which one it used.
- Whether the SDK's 2025 fallback lists the same tools as its 2026 path, for clients on each.
